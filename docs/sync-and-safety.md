# 同步、数据安全与冲突

[返回首页](../README.md) · [快速开始](quick-start.md)

Aster 日常编辑的是应用本地工作区，再通过所选来源同步。Agenda、Journal、Files、Search、Widget 和通知索引都可以重建；真正需要保护的是 Org 源文件和 Org Attach 文件。

## 支持的工作区来源

| 来源 | iOS/iPadOS | Android | 连接方式与说明 |
| --- | --- | --- | --- |
| Dropbox | 支持 | 支持 | OAuth 授权并选择远端文件夹；支持文件版本历史 |
| iCloud Drive | 支持 | 不支持 | Apple 平台使用系统文件夹选择器和安全作用域访问 |
| Nutstore | 支持 | 支持 | 账号、第三方应用密码和工作区文件夹；使用 Nutstore WebDAV |
| WebDAV | 支持 | 支持 | HTTPS 服务器 URL，可选账号与密码；适用于 Nextcloud 等标准服务器 |

Android 不提供 iCloud Drive，也不把应用内部工作副本或通用本地 Import 暴露为另一个工作区来源。

Nutstore 必须使用第三方应用密码，不要填写账户登录密码。通用 WebDAV 只接受带主机名、且不内嵌账号密码的 HTTPS 工作区 URL；HTTP URL 不会保存或连接。WebDAV 的账号和密码必须同时填写，或同时留空连接匿名服务器。密码在 iOS/iPadOS 保存在系统 Keychain，在 Android 由 Android Keystore 保护；Basic Auth 只通过 TLS 发送。

WebDAV 服务器即使只列出 `agenda/work/review.org` 这类嵌套文件、没有为每一级目录单独返回记录，Aster 也会从该路径恢复已经被证明存在的 `agenda/` 与 `agenda/work/`。因此 Files 中看到的目录也应能在 Agenda Sources、Journal folder 和 Event & Task Inbox 的路径选择器中使用。

## 一次正常保存如何流动

1. Aster 把完整、有效的 Org 修改保存到本地文件。
2. 相关路径的解析与界面投影增量刷新。
3. 同步引擎比较本地签名和远端修订。
4. 上传、下载或删除完成后记录各自路径的检查点。
5. 另一个客户端看到同一份普通文件。

界面先出现成功结果不代表只写了内存；反过来，网络暂时失败也不应回滚已经成功的本地源文件。

在 Aster 的 Files → Org 源码编辑器里保存 Agenda 来源目录下的文件后，Agenda、TODOs、Perspective、Search、Widget 和提醒会直接根据这个本地文件增量刷新，不需要等待上传、切换工作区或重启应用。云同步负责把已经保存的内容传到其他客户端，不是本机视图刷新的触发条件。刷新完成前继续输入的未保存文字也不会被较早的解析结果覆盖。

### 下一版 iOS/iPadOS 的同步保护（未发布）

上传和同步删除会检查刚才比较过的远端版本；版本已变化就停止，不强行覆盖。WebDAV 登录页、不完整或越界的目录结果也会报错，不再当成远端空目录处理。

WebDAV 同步替换或自动删除已有文件时，需要服务器提供强 ETag。缺少可靠版本信息时会明确报错，不降级为无条件写入。在 Files 中主动删除仍是独立的用户操作。iCloud 的写入、移动和删除通过系统文件协调器执行。

冲突比较打开后，如果本地源文件又被修改，旧选择会被拒绝，比较界面会换成最新本地内容。重新核对后再选择，后续编辑不会被旧快照覆盖。

## Apple Reminders 互操作文件（仅 iOS/iPadOS）

在设置中明确启用 Apple Reminders 后，Aster 会在工作区完成验证后同步，并在每次回到前台时继续同步。自动触发不会自行请求权限，当前状态会直接显示在设置开关旁。

Aster 只通过工作区根目录中独立托管的 `apple-reminders.org` 映射系统提醒事项。这个托管文件会自动出现在 Agenda 和 TODOs 中，不需要再把工作区根目录设为 Agenda 来源。

系统 Reminder 的“到期”固定映射为 Org `DEADLINE`，不会混成表示计划开始工作的 `SCHEDULED`。带时间的 Reminder 会保留准确时刻，只有日期的 Reminder 仍保持仅日期。

简单且不设结束条件的每天、每周、每月或每年重复会显示成保持原节奏的 Org `++` repeat。带结束条件或复杂筛选的重复仍由系统维护，Aster 不会把它简化成不准确的 Org 规则。

完成同步来的重复条目时，由 Apple Reminders 推进下一期，Aster 再同步下一条。两边不会各推进一次。

同步完成后，托管条目与普通 Org 条目共用 Aster 的展示规则。过期的 `DEADLINE` 和 `SCHEDULED` 都显示相同的“已逾期”“逾期 1 天”或“逾期 N 天”状态，不会因为来源是 Apple Reminders 而采用另一套计算。

普通工作区 Org 任务不会导出到 Reminders App。不过，只要条目已经进入 Aster 并有具体时间，Aster Notifications 就会继续发送提醒；从 Apple Reminders 同步来的条目也不例外。通知副标题会显示本地化的到期日期和时刻。

在 iPhone 和 iPad 上，Aster Notifications 默认开启“提醒数量角标”，也可单独关闭。它显示已经到达有效提醒时间、但仍未完成的定时任务数量。每个任务只计一次；普通日历事件和持续提醒的后续通知不会重复增加数量，关闭该选项会清除 App 图标角标。

若 Reminders App 的系统通知也已开启，两个 App 都可能提醒。这是明确保留的行为。

只有完全没有 Reminder 标识的托管 Org 标题才能创建新的系统提醒。已有标识失效不代表可以创建另一条同名提醒。

托管文件确实不存在时，首次同步可以创建它。如果文件已存在但无法读取、不是有效 UTF-8，或 EventKit 没有返回提醒列表，同步会停止并显示错误。Aster 不会把失败当成空文件或旧文件覆盖。

同步期间发生的本地修改也会保留。Aster 会提示源文件已变化，不会用稍早生成的结果替换它。

### 逐条比较与标准 Org 输出（下一版 iOS/iPadOS，未发布）

Aster 按每条 Reminder 的 ID 比较本地、系统和上次成功同步的字段，不再用整个文件的修改时间判断每一条谁更新。只改本地就导出，只改系统就导入；没有变化时不重写文件。

托管文件没有变化时，这次同步不会重新加载工作区，也不会额外安排一次云同步；仅更新设备上的同步基线也一样。普通的前台云同步检查仍然保留。

在 Aster 中完成、重新打开或编辑托管条目后，只要已获得“完全访问”，应用会立即请求一次 Apple Reminders 同步。如果此时已有一轮同步在运行，Aster 会保留一次后续同步，不需要切出应用再进入。

已有基线后，如果两边都改了同一条，同步会停止并指出需要核对的提醒。请比较 `apple-reminders.org` 与 Reminders App，将这一条需要保留的字段调整一致后再同步；这时不能靠反复重试解决。

设备第一次同步时，可能已有托管 Org 文件，但还没有设备私有的逐条基线。此时，Apple Reminders 当前快照中能找到的 ID 会导入系统状态来建立基线，包括系统中的完成状态；这不再被当成双向编辑冲突。

如果第一次快照中找不到某个 ID，Aster 会要求核对，不会静默删除。只有没有 ID 的标题才会新建系统提醒。已有基线后，本地未修改的条目可以随系统快照刷新；本地也被修改的缺失条目先保留并要求核对。同步基线保存在设备本地元数据中，不是另一份可编辑任务文件。

生成的文件自带 `TODO | DONE` 定义，计划行位于属性抽屉之前。下面是托管条目的结构示例，ID 由同步生成，请勿复制示例 ID 到实际文件：

```org
#+TODO: TODO | DONE
* TODO Review notes
DEADLINE: <2026-09-05 15:00>
:PROPERTIES:
:APPLE_REMINDER_ID: example-only
:APPLE_REMINDER_LIST: Reminders
:END:
```

## Android 通知边界

Android 版不创建 `apple-reminders.org`，也不把普通 Org Task 导入或导出到某个假想的 Apple Reminders 等价服务。**Aster Notifications** 从当前 Agenda 来源中带具体时刻的条目重建本地提醒计划；Android 13 及以上只在用户从设置明确启用时请求通知权限。

通知中的 Complete 和 Snooze 会回到同一个工作区写入边界，不能只改一份通知缓存。Android 使用系统允许的非精确闹钟能力，不要求用户授予精确闹钟权限。卸载、清除应用数据或断开工作区会影响本机通知计划，但不会改变云端 Org 文件。

## 冲突不会被静默覆盖

如果同一个文件在上次同步后本地和远端都发生变化，Aster 保留两份并要求明确处理，而不是猜测哪一份“更新”。解决冲突前，新的同步和 Dropbox 版本恢复可能会暂停。

处理前建议：

1. 先阅读两份源文本，特别检查刚修改的标题、附件链接和属性抽屉。
2. 选择应成为当前版本的一份。
3. 必要时先在其他工具中手工合并，再让 Aster 重新同步。
4. 不要在尚未理解冲突时连续点击重试或删除文件。

## 错误提示怎么判断

- **网络中断、超时、服务暂不可用**：稳定网络后重试；本地文件仍在。
- **授权失败或失效**：只有这类错误需要在 Settings 重新连接账号。
- **Dropbox rate limit**：等待一段时间再同步，反复重连不会更快。
- **远端文件尚未下载**：等待完成后再预览或移动。
- **冲突仍未解决**：先处理冲突，再继续同步或恢复历史版本。

普通瞬时网络错误不应该一律提示“Reconnect”。如果你仍频繁看到错误的重连建议，请提交包含版本、网络状态和复现时机的反馈。

## Dropbox 版本历史

长按 Dropbox 文件可查看其远端版本历史，预览文本或图片版本，并确认恢复。保留期限由 Dropbox 套餐决定；Aster 最多展示最近 100 个版本。

恢复前需要：

- 当前同步已经完成。
- 没有未解决冲突。
- 该版本仍在 Dropbox 当前路径和保留期限中。

恢复后的内容重新走正常下载、解析和界面刷新，不会写入一个 Aster 专用历史库。

## 同步不是备份

同步会传播正确修改，也会传播删除、错误编辑和已选择的冲突结果。至少保留一份不参与实时同步的备份：

```text
workspace/
├── agenda/
│   ├── inbox.org
│   └── data/...
├── journal/
│   └── ...
└── notes/
    ├── research.org
    └── data/...
```

只备份 `.org` 而遗漏相邻 `data/`，会丢失 Org Attach 文件。

## 断开工作区前

- 确认最新修改已出现在云端或独立备份中。
- 记录 Agenda Sources、Journal folder 和 Event & Task Inbox 的相对路径。
- 明白“清除本机镜像”和“删除云端内容”是不同操作，认真阅读确认文案。
- 重新连接后检查路径角色；不要仅凭首页有条目就认为整个目录已同步。

## 公开反馈中的隐私

不要上传：

- Dropbox、Google、WebDAV Token 或授权回调。
- WebDAV/Nutstore 密码。
- 完整私人工作区或未脱敏截图。
- 用户姓名、邮箱、绝对本机路径和附件原件。

尽量创建一个只有几行 Org 的测试文件复现问题。无法公开复现数据时，先描述结构和行为，不要把敏感内容放进 GitHub Issue。
